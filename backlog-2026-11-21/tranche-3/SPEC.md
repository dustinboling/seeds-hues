## 0. The one rule that governs all of Tranche 3

**Tranche 2 changed names and kept rendering still. Tranche 3 changes behavior and keeps the document still.** Every URL in this tranche server-renders the same content after the build as before it — same results, same counts, same selected states, same copy — for a first paint, a refresh, a shared link, and a no-JavaScript visit. What changes is what happens *after* hydration on surfaces a visitor is already looking at, what a form asks and in what order, and which HTTP status an out-of-range page returns. Three consequences, stated now because they decide arguments later:

1. **The enhancement layer is never the only layer.** If a behavior in §§2–5 cannot be expressed as "the server document is correct, and hydration makes it faster," it is mis-specified. The no-JS floor is not a fallback apology; on the waitlist (Item 3.2) it is a fully working flow.
2. **Behavior contracts are stated as observables.** Every normative claim below can be watched happening — a focus position, a history-entry count, a network log with no beacon in it, a status code. Implementation shapes named in this spec (payloads, endpoints) are normative only in their *contents*; the mechanism that delivers those contents is the pipeline's engineering choice, and §8 tests the observable, not the mechanism.
3. **One pattern, learned once.** Filters, sort, and applied-filter removers behave identically on every surface that carries them, because the shopper who learned them on `/variety` must not relearn them on a crop page. Where a surface legitimately differs (the seller State cloud's layout, search's relevance order), the difference is named in this spec as a settled exception with its reason — never left as an accident of separate builds.

### 2.4 Per-option counts — the contract (normative)

Baymard's highest-impact filter improvement, and the half of NUX-01 that makes the other half usable: a shopper sees what a tap will do *before* the tap.

1. **Definition.** An option's count is the number of results the surface would show with **that option selected and every other group held at its current selection**. The "All" option's count is the total under the other groups alone. On `/seller`, the State cloud's existing counts already satisfy this definition (only one group exists there) and do not change. On the variety-detail listing filter, counts are the listing counts its count line already states; no per-option counts are added to its two chips (a two-option toggle whose outcome the count line announces — adding numerals to both chips would duplicate the line, not inform).
2. **Rendering.** The count follows the option label inside the chip: muted numeral, then a screen-reader-only unit ("12 varieties" / "3 crops" / "9 sellers") — the StateFilter's shipped pattern, generalized. Counts are part of the server-rendered first paint and of every in-place update payload (§2.5.6); they are never computed on the client from a loaded page.
3. **Zero counts.** An option whose count is 0 renders its `0` and **stays operable**. The count itself is the prevention Baymard asks for; disabling the option would hide *why* the set is empty and strand a shopper who wants to change two groups in sequence. Selecting a 0-count option lands on the designed zero-results state (§2.6.3) with its recovery — a state this spec requires on every filtered surface.
4. **Freshness.** Counts describe the catalog as last checked, like every other number on the site; no "live inventory" language is introduced. A count and its results always come from the same payload, so the two can never disagree on screen (the class of defect Priya's dedupe closed must not reopen through a side channel).
5. **Counts under multi-select Hue (applies only if PB-2 is ruled for multi-select).** A hue option's count is the number of results if that hue were **toggled** from its current state, with every other group held at its current selection: for an **unselected** hue, the results with that hue **added** to Hue's selected set; for a **selected** hue, the results with that hue **removed** from the set. When counts are computed for options in any other group, Hue's current selected set is held as it stands. Hue's "All" chip under a partial set **clears the set**; its count is the total under the other groups alone (the §2.4.1 "All" definition, applied to the set). This paragraph reconciles §2.4.1's "that option selected" wording with §10 PB-2's toggle wording: under multi-select, "selected" in §2.4.1 is read through this paragraph for Hue, and §2.4.1 stands unchanged for every single-select group.

### 2.5 In-place behavior — the contract (normative)

The Q7/B9 joint spec (my consultation §7 Q7, Mina's visual half) is the base text; this section extends it from one toggle to the multi-group browse model. Every clause is an observable.

1. **Classification.** Every control in §2.2's table, plus the sort control (§5.2), plus the applied-filter removers and Clear All (§2.6), is local-scope: it re-scopes or re-orders content the visitor is already looking at. Once hydrated, activating one updates the results region, the count line, the applied row, the per-option counts, and pagination **in place** — no document navigation, no route skeleton, no repaint of header, hero, or strips.
2. **Preservation.** Scroll position does not move; the activated control keeps focus and stays mounted (state changes must not remount chips — keys are stable across selections); surrounding content does not repaint. If a proposed implementation breaks any of these, it is wrong however it is built (§0.2).
3. **Budgets.** Selected dress applies in the same frame as the tap (≤ ~0.1s). Updated results land within ~400ms (Doherty). Data is a server round-trip here (unlike the variety-detail toggle, whose data is on the page), so: prior results stay visible until the replacement is ready, then swap **once**; no spinner and no skeleton for a sub-second update; if an update genuinely exceeds 1s, a quiet busy indication on the results region (`aria-busy="true"` on the region, removed on swap) is the only permitted addition — never a skeleton swap.
4. **URL and history.** State lives in the URL (the existing query parameters, unchanged names) via the History API. One deliberate change = exactly one history entry. Re-tapping the active option is a no-op (no entry, no announcement, no fetch). Hydration, re-renders, and programmatic sync create none. Back/Forward restore the prior state **in place** — selected options, counts, results, applied row, and page together — and Back never exits the page over a filter change. A filter or sort change resets pagination to page 1 (the existing `chipHref` discipline: `?page=` is never carried across a filter change).
5. **Pagination is the boundary of this contract.** Moving between pages of an unchanged filter state remains true navigation (each page is an indexable document with its own canonical discipline, already settled in the pages' metadata). Pagination links keep today's `scroll={false}` + clamp behavior. Back/Forward *across a pagination entry* therefore behaves as it does today; Back/Forward across a *filter* entry behaves per §2.5.4. The two are distinguishable in the history stack by their URLs, and the gate drive (§8) exercises both.
6. **The update payload (contents normative, mechanism free).** One request per deliberate change returns, atomically: the results for page 1 of the new state, the total, the per-group per-option counts under the new state, and the applied-filter set. The client never assembles a view from two responses. A slower earlier response never overwrites a newer selection (last selection wins; stale responses are discarded). On failure, the current results, counts, and URL all stay exactly as they were, the control's selected state reverts to the last good state, and one in-place error line appears with the applied row ("That filter didn't apply — you're still seeing the previous results. Try again." — Wren confirms final wording), announced once via `role="alert"`; it is not repeated per retry.
7. **Bookkeeping.** A local-scope change is not a page view: it fires no page-view analytics and no view beacon (`ViewBeacon` must not fire — §8 checks the network log), and it is not counted as one anywhere downstream.
8. **Semantics after enhancement.** Before hydration and without JS, chips are links with `aria-current="true"` (today's floor, unchanged). After hydration each group becomes buttons with `aria-pressed` — exactly one pressed per single-select group, the shipped SellerFilterSection pattern generalized — inside the existing labeled group structure; no element ever carries both `aria-current` and `aria-pressed`. Selected state is never carried by color alone (Tranche 2 §4.2's dress: border + ground + weight + the pressed state). Targets stay 44px. Under PB-2's multi-select Hue, Hue's buttons are independent toggles (any number pressed, including none = All).
9. **Announcement.** Each surface's count line is a **persistent** live region — present in the document before any change, `aria-live="polite"`, `aria-atomic="true"`, never remounted — whose text changes exactly once per deliberate change, in step with the visible results, announcing no loading or intermediate states. This requires two repairs inside this item: the home count line renders unconditionally (at rest it reads the unfiltered crop total, e.g. "124 crops"; the line's current conditional mount is a defect this item closes), and the `/crop` index count line gains the region attributes. `/variety` (`#variety-results-count`), `/crop/[slug]` (`#crop-results-count`), and variety detail (`#variety-listing-count`) already comply. On `/search` the results `<h2 id="results-title">` remains the region (it exists whenever filters exist on that surface, since filters render only with a query).
10. **Resilience.** Any motion in the swap honors `prefers-reduced-motion` (the listing cascade's rules are the model; browse grids may reuse `--duration-filter-item` / `--ease-filter-settle` or swap without motion — motion is not required, stillness is not a defect). No layout shift at 320px or 200% text resize when a region updates; selected-state meaning survives forced-colors mode (real borders + weight + pressed state, per Tranche 2 §4.2).

### 2.6 Applied filters and Clear All (normative)

1. **The applied row.** Directly above the results region, below the strips, one row shows what is shaping the view: one `.chip-filter.chip-removable` per active group (Tranche 2 §4.4's modifier, inherited exactly — drawn × glyph, one hit target, glyph never separately focusable), labeled `"{Group}: {Value}"` ("Hue: Pink", "Season: Cool season"), with an accessible name that starts with "Remove" and names group and value ("Remove the Hue filter, Pink"). Under PB-2 multi-select, Hue contributes one remover per selected hue. The sort control, when non-default, is **not** in this row (it is an ordering, not a filter; its state lives in its own control, §5.2).
2. **Clear All.** When at least one filter is active, the row ends with a Clear All control (`.chip-filter`, label "Clear all filters") that resets every group to All in one action — one history entry, one announcement, one update. With no filter active, the row and Clear All are absent (the row never renders empty). On `/seller`, the cloud's "All states" chip remains and the applied row shows the single State remover + Clear All is omitted there as redundant (one group, one remover — a second control doing the identical thing would be noise; recorded as a bounded exception).
3. **Zero-results state.** Every filtered surface renders its designed empty state *inside* the results region: it names the situation in the surface's existing copy voice (the shipped `EMPTY_BROWSE` / crop / search texts stand), keeps the applied row visible above it (so the shopper can see what to remove), and offers Clear All in place. If the action that produced the empty state unmounts the activated control, focus lands on the applied row's Clear All — the playbook's one stated focus exception, applied uniformly. Home and `/crop` index, which today render a silently empty grid under a filtered count, gain this state in this item.
4. **No-JS floor.** The applied row is server-rendered from the URL state: removers are links to the same URL minus that group, Clear All is a link to the surface's base path (carrying `q` on `/search`), exactly as `chipHref` already computes group changes. The floor may navigate; it may never show a remover that does nothing or a filtered list under an unfiltered URL.

## 3. Item 3.2 — Waitlist flip (alert first, account in place) + no-JS fallback (UX-05, U5.2)

### 3.1 Current state (verified, `origin/main`)

- **The wall is intact.** A signed-out visitor on a zero-seller variety page meets the full `SignupFields` set inside `WaitlistBlock.tsx`: name, email, phone (required), ZIP (required), account-type radios, the SMS opt-in with its consent copy, and Turnstile — seven asks before one alert. Quinn rated the requirement U5.1 (Nielsen 2); my UX-05 rates the flow major. Dustin ruled for the flip on 2026-11-20 (pushback P2, in the team's favor, over his own approved Phase 3 account spec): *the alert is set with contact + channel alone; the minimal account is created in place as part of that submission; profile extras are asked afterwards or not at all.* The ruling is built nowhere.
- **What is already right, and stays.** The signed-in path is one click. The create-and-join submission already creates the account *in place* as part of joining (one submit, no page change) — the flip is about what that submission *asks*, not where it happens. The post-join machinery is the best state design on the site: the celebration + next-step card, States A–D (verified / unverified-with-code / held), the deliberate focus moves to the success heading and back, `CodeEntry` inline. None of it is redesigned here.
- **The recognized-contact path is a dead end.** The form's only answer to an existing account is the line "Already have one? Sign in, then come back" — a link to `/account` that loses the variety and the visitor's place, exactly what the P2 ruling forbids ("recognized contacts verify inline, never a dead end").
- **The server requires the wall.** `CreateAccountSchema` (`v2/lib/services/accounts.ts`) requires `name`, `email`, `phone`, and `zip` for every create, including `join_variety` creates. The flip is therefore **not a form-only change**: it carries a service/schema contract change (§3.3), and this spec states it as a build input rather than letting the build discover it.
- **Without JavaScript, the waitlist does not exist (U5.2, verified).** `WaitlistBlock` is a client component; the server renders the block's shell with an sr-only "Loading waiting-list status…" and two skeleton bars, and the form, the join button, and the joining instructions are all client-rendered after a status fetch. On the one page type where the waitlist is the *only* action, a no-JS or failed-JS visitor gets a loading message that never resolves.

### 3.2 The flipped flow — target contract (normative)

The flow is: **variety → contact + channel → done.** States, in the order a visitor meets them:

1. **The alert step (signed-out resting state).** The block shows: the existing heading and one-alert/leave-any-time copy (unchanged — Quinn found it the clearest pre-commitment copy in the audit); an **Email** field (required); a **channel choice** as compact radio rows (my Q4 ruling: compact rows in this flow, never selectable cards — a weightier control re-imposes the account burden this item removes): "Email only" (default) / "Email and text"; and the submit button, "Join the waiting list". Turnstile rides the submission as today, invisibly to the contract. **Name, ZIP, and account type are not on this step and are not required by it.**
2. **Text channel selected → phone appears.** Choosing "Email and text" reveals a **Phone number** field directly under the radio (required for that channel), carrying the existing explanation ("Your email + phone are how you sign in — there's no password. We never show your phone number.") plus the SMS consent copy when the text channel is chosen (the consent text itself is settled copy and does not change; its placement moves from an opt-in checkbox to the channel choice it describes — the choice *is* the opt-in, and the consent copy sits beside it). Revealing the field never moves focus; focus stays on the radio the visitor just chose. Switching back to "Email only" hides the field and the phone is not submitted.
3. **Submission creates the minimal account in place.** One submit: the account is created with exactly what the alert needs (email; phone iff text chosen) and the variety join is recorded, in the same request pattern the block uses today (`join_variety`). The visitor never leaves the block, and the success machinery (§3.1, States A–D) takes over exactly as it does today — including the email-verification hold: alerts stay held until the email is confirmed via the inline `CodeEntry`, with the held reasons stated in the next-step card. The flip does not weaken verification; it removes profile collection from in front of it.
4. **Recognized contact → verify inline.** If the submitted email belongs to an existing account, the block does **not** show an error and does **not** link away. It moves in place to the verification state: "This email already has an account — we've sent a 6-digit code to {email}. Enter it to join this waiting list." with the shared `CodeEntry` in the block. On verification, the join completes — the session is established **at verification, in that step** (a new moment: no existing flow establishes a session there; see §3.3's recognized-contact contract) — and the standard success state renders. A wrong or expired code follows §4's behavior contract. The "Sign in, then come back" line is deleted.
5. **Finish-your-account step (optional, after the goal).** After joining — in the success state's next-step card area, below the alert status, never interleaved with it — a dismissible, clearly optional step offers the deferred profile: "Want to finish your account? A name and ZIP set your growing zone — you can do this any time, or not at all." Name, ZIP, and account type live here and only here; skipping or dismissing changes nothing about the alert. What the visitor entered (email, phone) is never re-asked (WCAG redundant-entry rule). This step also appears, equivalently, in the account panel for waitlist-created accounts until completed — same fields, same optionality.
6. **Signed-in path.** Unchanged: one-click join, existing states, existing leave action.

**Errors on the alert step** follow §4's contract (inline, associated, data preserved, plain mapped copy). One flow-specific rule: a duplicate-email response is never phrased as an error — it is the recognized-contact transition (§3.2.4), a normal path with its own copy.

### 3.3 Service contract inputs (normative contents, for the pipeline)

- Account creation with `join_variety` accepts the minimal set: `email` required; `phone` required **iff** the text channel is chosen, absent otherwise; `name`, `zip`, `farm_owner` not required on this path (name unset, zone null — `PublicUser.usda_zone` already admits null — account type defaults to gardener until §3.2.5 is completed). Whether the relaxation is scoped to `join_variety` creates or general to all creates is the builder's call; the observable contract is that the waitlist path never demands the deferred fields, and the `/account` create form keeps working exactly as today until Item 3.3's pass reaches it.
- The join records the chosen channel; SMS consent timestamping follows the existing consent discipline (the current `sms_opt_in` records it today).
- **Sign-in seam, named honestly:** sign-in is email + phone. An account created by the flip without a phone cannot use that pair until a phone exists. The contract this spec sets: such an account is never a dead end — when its owner returns, the variety-page block recognizes the email and verifies by code in place (§3.2.4), and alerts are manageable from that verified state. The `/account` page's own accommodation is the one piece this spec leaves open (§11.1), with a recommended default recorded there, because it touches the credential model and deserves Dustin's explicit eye rather than a sub-clause here.
- **Recognized-contact service contract (the service half of §3.2.4, normative).** (i) Submitting an email that belongs to an existing account to the join path **issues a verification code to that email without a session**, and discloses nothing about the account's existence beyond what §3.2.4's copy already shows the submitter themselves. (ii) Code issuance on this path is **rate-limited** — the limits are the existing verification service's limits, referenced here as the governing values; the create path's `enforceLimits: false` precedent is **explicitly not carried over** to this unauthenticated code-issue path. (iii) The pending join — the variety the code was issued for — is recorded with the issued code, so that (iv) **successful verification establishes the session at verify time and completes the pending join for that variety in the same step**, after which §3.2.4's success state renders. No part of this contract may be satisfied by linking the visitor to `/account`.
- **Turnstile on the non-JS path:** the form-encoded endpoint in §3.4 is exempt from Turnstile under the disposition in §3.4.5; Turnstile remains required on the JavaScript path exactly as today. The exemption is gated on Dustin's ruling (§11.4) — Item 3.2's build does not start until that ruling lands.
- **Storage representation of the minimal account (for the build, not the visitor).** The users table stores `name`/`phone` as NOT NULL with `""` defaults, and `PublicUser.name`/`phone` are non-nullable strings — so "name unset" and "no phone" in this contract are in practice the empty-string sentinel. The account panel and §3.2.5's finish-your-account step must treat `""` as unset (the step is offered, the fields read as unfilled), and no surface may render the sentinel as a value.

### 3.4 No-JS fallback — the floor is a flow (normative)

1. **Server render.** The variety page server-renders the waitlist block's real content for the unknown/signed-out state: heading, explanatory copy, and the §3.2.1 alert-step form as a plain HTML form (email, channel radios, phone field present in the markup for the text channel). In the floor form the phone field is **visible, labeled as needed only for text alerts, and never carries the `required` attribute** — native validation must never block an email-only no-JS submission; the server enforces phone-required-iff-text-chosen per §3.3. The skeleton/"Loading waiting-list status…" server output is **deleted** — a loading shell may still appear *after* a JS status fetch begins, but it is never the server document.
2. **Plain POST join.** The form posts without JavaScript to the account/waitlist endpoint (a non-JS form encoding of the same create-and-join contract), which on success redirects back to the same variety page with a waitlist status parameter; the server renders the corresponding state into the block: joined-and-verify ("You're on the waiting list for {variety}. Alerts start once your email is confirmed — enter the 6-digit code from your email:" + a plain code form that also posts without JS), recognized-contact (the code state, per §3.2.4), or joined-and-active. Status parameter names and values are the builder's, but the states and their copy obligations are this contract's, and no state may be reachable only with JS.
3. **Enhancement.** With JS, the block hydrates into the session-aware component it is today (signed-in one-click, on-list states, leave) — the enhancement replaces the floor form only when the status fetch has resolved; **if the fetch fails, the floor form stays on screen** (with a brief note that account status couldn't be checked) instead of an eternal skeleton. A signed-in visitor who submits the floor form is handled by the recognized-contact path — the floor is correct for every session state, which is what makes it a floor rather than a signed-out special case.
4. **The listing state gate stands.** The block renders only when the variety has no sellers (`status.variety.listed` gate, today enforced client-side after the fetch; the server render applies the same rule from the page's own data — a zero-seller page is exactly where the block belongs, and a listed variety's page must not gain a server-rendered join form for a list that does not exist).
5. **Turnstile disposition — (a), the exemption, stated in full.** Turnstile's token is minted by Cloudflare's JavaScript widget and its verification fails closed on a missing token, so a plain no-JS POST can never present one; without a stated disposition the §3.4.2 flow cannot succeed. The disposition is: **the non-JS form-encoded create-and-join endpoint (§3.4.2) is exempt from Turnstile.** The compensating controls, named so the exemption's abuse ceiling is bounded by design rather than by hope: **(i)** the email-verification hold of §3.2.3 — alerts stay held until the email is confirmed by the inline code, so an unverified submission activates nothing; **(ii)** the site's existing rate limiting, which applies to this endpoint as it does to the create path (and, on the recognized-contact code-issue path, per §3.3's rate-limit clause); **(iii)** Turnstile remains **required on the JavaScript path** exactly as today — the exemption covers only the form-encoded no-JS endpoint, nothing else. This exemption is a security posture decision, not a design detail this spec may absorb silently: it is carried to Dustin (via Hue) as §11.4, and **Item 3.2's build is gated on his ruling** (§9). Check 3.2-E stands as written once this disposition and that ruling both exist.

## 4. Item 3.3 — Field-state set: behavior-contract inputs and sequence (F-20, Ada A4)

**Ownership, stated first because this section is deliberately not a design:** Mina + Ada design the field-state set itself — the visual treatments for resting / focus / error / disabled / success, the per-field error presentation, the summary box — and Ada's A4 association pattern is hers. This section is my seat's contribution to their work: the **behavior contract** the set must satisfy on every public form (the contract the joint recommendation §4.1.5 settled and my consultation's B5 ruling ordered ahead of component promotion), the **complete form inventory** it must cover, and the **sequence** (§9) that keeps Items 3.2 and 3.4 from building forms twice. Where this section needs a value only Ada can give, it says so and flags it; it invents none.

### 4.1 Current state (verified)

- Public `.field` defines resting + the global focus ring only; no error, disabled, or success treatment exists in the public component layer (Mina F-20). Every public form renders errors as one form-level `role="alert"` paragraph in `text-warn` after the submit button (CreateAccountForm verified verbatim; ReportForm, SignInForm, CodeEntry, WaitlistBlock the same pattern), with no `aria-invalid` and no `aria-describedby` anywhere on the public side (Ada A4: "public forms still do not").
- The correct pattern already exists in-house: admin `seller-sheets.tsx` / `variety-sheets.tsx` ship per-field `aria-invalid` + `aria-describedby` wired to per-field error ids, with a summary box whose entries anchor to fields. A4's fix is a port, not an invention — in admin dialect, which is why it is Mina's design job to bring it into the public system rather than a copy-paste.
- Copy mapping is half-done: ReportForm (`report-errors.ts`) and — since Tranche 1.5 — AddYourFarmForm (`farm-errors.ts`) translate server failures into plain, field-specific sentences. The account forms and the waitlist surface the API's message raw. Tranche 1.5 closed D6.1 (raw validator text) for one form; the contract below closes the class.

### 4.2 The behavior contract (normative — Mina + Ada design *to* this)

1. **Errors live beside their field.** On a failed submit, each invalid field shows its message in a slot adjacent to the field, the field carries `aria-invalid="true"`, and the message carries the id the field's `aria-describedby` points to (Ada's exact A4 prescription — adopted verbatim as the contract; any deviation needs her ruling, flagged in §4.4). Hint text and error text never fight for the same slot: when an error shows, the field's describedby includes both hint and error, in that order.
2. **Focus goes to the problem.** Single error: focus moves to the invalid field on failed submit. Multiple errors: a summary appears at the top of the form, focus moves to the summary, and each summary entry is a link whose activation moves focus to its field and whose text is character-identical to the inline message beside that field (the GOV.UK pattern Quinn's U6.3 cites). No summary for a single error — it would be ceremony between the user and the fix.
3. **Data is never the price of an error.** A failed submit never clears, resets, or remounts away anything the visitor typed, on any form, including a server round-trip failure and a Turnstile failure. (Most public forms satisfy this today by construction; the contract makes it a gate-checked property, because the waitlist rebuild in §3 touches the form where it matters most.)
4. **Requirements are stated before failure.** Every rule a field enforces is visible at the field before submission: minimum lengths, formats, and patterns in the hint (Quinn U6.2's two live cases — Add Your Farm's 10-character About minimum and one-per-line Varieties format — are stated as *rules* in their hints under this contract, not merely described; the ZIP hint states "5-digit"). A validation that can only be discovered by failing it is a contract breach, whoever builds the form.
5. **Copy is mapped, plain, and field-specific.** No raw validator string, error code, or API `detail` text reaches a visitor on any public form — every form gets the report/farm mapping treatment (a per-form mapping layer, or server messages written to the same standard; the mechanism is the builder's, the property is the contract's). A message names the field's subject in the visitor's words, states the problem, and states the fix.
6. **Busy never strands.** Submitting disables the submit control only — never a fieldset of data-bearing controls (the BusyForm defect class; Ada's §10 gate criteria are adopted: focus is never dropped to `<body>` by a submit, and the busy state is exposed — submit label change plus a `role="status"` announcement or a headed post-submit state). Entered data stays editable-visible (greyed is a treatment; gone is a breach).
7. **Success is a state, not a silence.** Every form's success keeps or gains: a headed confirmation in place (focus moves to it per the waitlist's existing discipline), what happens next and when, and the way back or onward. The existing praised successes (Add Your Farm, Report, waitlist) are the standard; account create/sign-in states are brought to it.
8. **Choice groups ride the same contract.** Radio/checkbox groups validate as a group: the error attaches to the group's `<fieldset>` (describedby on the group, focus to the group's first control or its summary entry), and the selectable-card vs compact-row split ruling stands (cards for weighty choices — report type, account type at create; compact rows in the waitlist flow, §3.2.1).
9. **The native select stays native.** Behavior is the platform's (settled, joint recommendation §4.1.5); Mina's set styles it into the field system, and ReportForm's longhand duplication of `.field` (Mina F-22) is retired by the set — after this item, every public field consumes `.field` and its states, and a grep for hand-rolled field class strings on public forms returns zero.
10. **CodeEntry is a first-class citizen of the set.** Ada's W-2 fix lands here, exactly as she prescribed (`aria-invalid` + `aria-describedby="{idPrefix}-code-error"` on the input, that id on the error paragraph), in all three contexts that consume the component (waitlist, account, admin sign-in code page — the last by consumption, not by an admin redesign). Two Quinn minors ride the same component touch and are adopted as contract: the code's lifetime is stated in copy wherever a code is requested (U7.1 — the admin code page already states its TTL; the public component must match), and the field accepts a pasted code with spaces without truncating it before stripping (U7.2 — the `maxLength={6}`-vs-strip conflict is removed; the field accepts the spaced form and normalizes on input or submit).

### 5.3 Search repair (UX-06, U1.1–U1.3, + Ada AD-2)

**Current state (verified).** Three defects, one component (`SearchBox.tsx`) plus one service merge:

- **Auto-open (UX-06) is byte-for-byte the baseline's.** The suggestion effect is keyed on `q`, which initializes from `defaultValue`; on the `/search` results page the box mounts with the submitted query and the effect fetches and calls `setOpen(true)` on mount — the panel opens over the results it duplicates, with no user action in the box.
- **Ranking (U1.1) has a named root cause.** Varieties rank properly inside their own list (FTS tiers: exact → prefix → full-text, has-listings tiebreak). But the autocomplete consumes the combined `results` array, which the service builds as `[...crops, ...series, ...varieties, ...sellers]` — type order, not match quality — and crops/series/sellers match by unranked substring `LIKE`. Quinn's probe is reproducible from the code: `q=ali` returns four substring-matched crops ahead of Alison, a prefix-matched variety, at position 5.
- **No visible empty state (U1.2).** On zero suggestions the listbox stays `hidden`; "No suggestions. Press Enter to search." exists only in the sr-only status line. A sighted user sees nothing happen and cannot tell broken from empty (H1). A fourth gap rides along: misspellings get no recovery (U1.3 — "alsion" returns the generic zero-results page; the copy tells the user to check the spelling they half-remember).

#### 5.3.1 No-auto-open (normative)

A SearchBox panel opens **only** in response to the visitor's own input in that box during this mount: typing (the existing 300ms debounce), or ArrowDown with results present. Concretely: the mount value of the field is *submitted text, not typed text* — no fetch and no open occurs until the field's value differs from its mount value, or the visitor explicitly requests suggestions by keyboard. Focus alone never opens the panel; `onFocus` may reopen only a panel the visitor's own typing produced in this mount. This holds on every SearchBox instance (home, search page, any future mount), and the results page is the acceptance surface (§8): loading `/search?q=zinnia` renders results with the panel closed, and it stays closed until the visitor edits the box.

#### 5.3.2 Autocomplete ranking (normative)

The combined list orders by **match class first, type second**:

| Class | Definition | Examples for `q=ali` |
|---|---|---|
| 1 — Exact | Name (or a variety's alias) equals the query | "Alison" for `q=Alison` |
| 2 — Prefix | A name, or a word of it, starts with the query (the varieties' existing tier 1; the same test applied to crops, series, sellers) | Alison (variety) for `q=ali` |
| 3 — Substring / full-text | Everything else that matches today (varieties' tier 2; substring `LIKE` matches) | Calendula, California Poppy, Chinese Lantern, False Indigo for `q=ali` |

Within a class: varieties first (keeping their tier order and has-listings tiebreak), then crops, series, sellers, each alphabetical. The probes that become acceptance checks: `ali` → Alison above all four substring crops; `Alison` → Alison, then Alison Valentini; `sweet pea` → the Sweet Pea crop first (an exact-name class-1 match beats combined-name prefix matches); `mother of pearl` → the single exact variety. **The results page's grouped layout does not change** (Crops / Series / Varieties / Sellers sections are a reading structure, and each group's internal order already follows the service's per-type ranking); this contract governs the autocomplete's combined list, which is where U1.1 lives.

#### 5.3.3 Visible empty state (normative)

When a visitor-typed query of ≥2 characters returns zero suggestions, the panel **opens with one non-interactive message row**: "No suggestions — press Enter to search." The row is not an option (never `aria-selected`, never activatable, Enter submits the search as today), it is marked `aria-hidden="true"` (the sr-only status line already announces the identical text — one message, two channels, announced once), and it replaces the current `hidden`-on-empty behavior. The failure state ("Suggestions unavailable. Press Enter to search.") gets the same visible row treatment with its own existing text. No spinner is added; the debounce window stays silent, as today.

#### 5.3.4 Did-you-mean (U1.3, bounded)

On the **results page's zero-results state only** (not the autocomplete), if a near match exists, the state offers it: "Did you mean **Alison**?" as a link to that result's search. Bounded candidate rule (the whole design): candidates are variety and crop names sharing the query's first letter with edit distance ≤2 (a transposition counts as 1), computed only when the result set is empty, over the name index the search already loads — at this catalog's scale (794 varieties, 124 crops) that is a small in-memory check, not a new search subsystem. At most one suggestion (the closest; ties break to the name with sellers, then alphabetical). If no candidate qualifies, the state is exactly today's (spelling guidance + the tell-us link), unchanged. The stray-space defect inside the quoted query in that copy (Quinn U1.4, cosmetic) is fixed in the same touch.

#### 5.3.5 Ada AD-2 — disposition: ruled INTO this item (active-row state mark)

Ada's addendum finding AD-2 (medium, WCAG 1.4.11): the autocomplete's active row is identified by a `bg-leaf-50` wash only — 1.2118:1 against the surface listbox ground, against a 3:1 floor — so a sighted keyboard user cannot see which suggestion Enter will activate. **It lands in this item** (the SearchBox is rebuilt here for §§5.3.1/5.3.3; splitting AD-2 out would re-touch the same component in a later tranche). The fix follows Ada's prescribed direction: the active row gains a **3px left rule in full-strength `leaf`** (`#1E4634` on surface = 10.42:1 ✓, comfortably past the floor), applied to the same `active` state that drives hover and keyboard alike (they are one state in the code, and stay one). The leaf-50 wash may remain as a redundant channel. The rule's exact geometry is Mina's to confirm in her visual pass on this item; the floor (a state mark ≥3:1, not carried by a wash) and the mechanism (a leaf-strength rule) are fixed here, and §8 recomputes the pair from the built CSS. ## 10. Pushback — for Hue to carry to Dustin

Specialists are expected to push back; these are mine. Both are designed completely under either ruling, and both are flagged *before* their builds dispatch (§9), so a ruling costs no rework.

- **PB-1 — The sort default should change to availability-first, and Dustin should rule it knowingly.** *The item as approved:* "a sort control (UX-03)." *What UX-03 actually found:* the harm is not the missing control, it is the default — alphabetical order buries buyable varieties under unavailable ones on the directory's core lists, and a control most visitors never touch does not fix a default every visitor meets. *My design (§5.2.4):* "Most sellers first" becomes the default on `/variety` and `/crop/[slug]`; A–Z remains one tap away and in the URL vocabulary. *The cost, stated plainly:* every list's first page changes visibly, the count lines stop saying "alphabetical" at rest, and anyone who has learned the current order relearns it. That is a bigger change than the item's wording suggests, which is exactly why it is carried here rather than folded in: if Dustin wants the conservative version — control added, A–Z default kept — §5.2.5 is fully designed and the build differs by one parameter's meaning. My recommendation stands with the finding: change the default.
- **PB-2 — Hue should become the site's one multi-select filter group.** *The settled model:* every group is single-select (joint recommendation's parity table; the data for Season/Sowing/Life cycle/State is genuinely single-valued per entity). *Where that hurts:* Hue is the exception in the data and in the shopper. A variety carries one hue, but a gardener shops a palette — "pink or peach zinnias" is a real, common intent the current model cannot express (my audit's UX-12 residue), and Baymard's research — the filter half of my playbook — finds multi-select *within* a category is what users expect, with single-select forcing friction and abandonment. The service already accepts a list for `colorFamily`, so the machinery costs nothing extra. *My design:* Hue (on `/variety`, `/search`, and crop pages) becomes independent toggles — any set of hues, OR within the group, AND across groups; counts recompute per §2.4 with Hue's own current set held for other groups' counts and each hue's count computed as "results if this hue were toggled"; the applied row carries one remover per hue; the URL carries repeated/comma `color_family` values in the existing parameter (encoding is the builder's, the parameter name is not new). Every other group stays single-select. *If Dustin declines:* Hue ships single-select on identical machinery — the difference is contained to the group's selection logic, and this pushback is recorded as considered-and-declined rather than never raised.

No other finding's prescribed fix is deviated from. Where this spec extends a finding, it says so in place (AD-2 and A3 ruled into their items with reasons, §§2.7/5.3.5; the search Sellers exclusion, §2.2; the seller-cloud Clear All exception, §2.6.2).
