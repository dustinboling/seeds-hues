# Seed Directory — User Accounts + Waiting Lists: Design

**Status:** DESIGN CONFIRMED FOR BUILD (Phase 3, after the Phase 2 filter deploy).
**Rename note (2026-11-16):** the product was renamed "Seed Finder" → **"Seed Directory"** (Dustin); this doc uses the new name. Domain and paths unchanged.
**Decisions locked by Dustin, 2026-11-16:**
- **Sign-in model: name + email + phone number, NO password, NO codes** — exactly the Hues site account model; sign-in is the email+phone pair.
- **ZIP code is REQUIRED at signup** (added 2026-11-16 evening): the signup form is name, email, phone, **ZIP**, plus the farm-owner declaration control. The USDA zone is auto-derived from the ZIP at signup and stored on the account (`zip` + `usda_zone`), so every account's zone is known from day one — powering personalized filters, assistant answers, and (later) zone-aware alerts. The IVR finish-setup flow treats ZIP as a required completion field too ("fully set up" includes ZIP on file). Privacy: ZIP is account data, never displayed publicly; features use the derived zone, not the exact ZIP.
- **Cloudflare Turnstile is REQUIRED** on account creation, sign-in, and waiting-list signup (server-side verification on the Worker; keys are Worker secrets, never in the repo).
- **Headline feature: per-variety WAITING LISTS** — "tell me when this variety is found at a farm."

---

## 1. What accounts unlock, in priority order

1. **Waiting lists (the headline).** A visitor joins the waiting list for a variety and is emailed the moment a listing for that variety is published at any seller. The zero-seller variety pages ("No sellers yet — currently unavailable") are the natural signup surface: every zero-seller page becomes a waiting-list page ("Join the waiting list — we'll email you when a farm lists it"). Varieties that already have sellers get the same control ("Email me if more farms list it" is OUT of scope for launch — launch notifies on first-found only; see §4 dedupe).
2. **Seller ratings/reviews** (secondary, Phase 3b). The canonical spec's ratings need accountable raters; accounts provide the identity anchor (one rating per account per seller, editable, with a moderation queue).
3. **Favorites / watchlist** of varieties + sellers (secondary, 3b — reuses the waitlist plumbing's identity, simpler data).
4. **Seller claim/manage** (secondary, 3b): a signed-in seller claims their page (claim verification stays email-based per the canonical spec; the account becomes the manage surface).
5. **Saved filters/preferences** (3b, trivial once sessions exist).

## 2. Auth model — confirmed, with the honest tradeoffs

**Model:** account = { name, email (unique), phone }. Create: submit the three fields + Turnstile → account created, session issued. Sign-in: submit email + phone + Turnstile → if the pair matches an account, session issued. No password, no emailed codes, nothing to forget.

**Why it fits Seed Directory:** the audience is gardeners, not power users; the Hues site already runs this exact model, so Dustin's visitors get one consistent pattern across his properties; the assets at risk are low-value (a waiting list, favorites) — there is no payment data, no orders, nothing worth a credential-stuffing campaign.

**The risks, stated plainly, and the mitigations built in:**
- *Anyone who knows (or guesses) a person's email + phone can sign in as them.* Both values are semi-public for many people. Mitigations: Turnstile + per-IP and per-pair rate limits on sign-in (e.g. 5 attempts / 15 min / IP, exponential lockout per pair); sessions are 30-day, HttpOnly, Secure, SameSite=Lax cookies holding a random 256-bit token (only its SHA-256 hash is stored); account pages show no sensitive data beyond name/email/phone and list memberships; a "this isn't me / secure my account" path lets the real owner freeze sign-in by contacting Hues (manual at launch scale).
- *Ratings abuse (Phase 3b):* one rating per account per seller, ratings from accounts younger than 24h are held for moderation, Dustin's review queue can remove ratings and ban accounts (ban = email+phone blocklist, same mechanism as `blocked_domains`).
- *Spam accounts / list pollution:* Turnstile on every entry point, email-format + phone-format validation, one waiting-list entry per account per variety (unique constraint), and the notification dedupe in §4 makes fake accounts useless for amplification.
- *Account recovery:* there is nothing to recover — if the email+phone pair is entered correctly, you're in. If a user changes their phone number, the old pair stops working; recovery = create a fresh account + a support note to Hues to merge waiting lists manually (acceptable at launch scale; a self-serve "update phone with email confirmation link" is a 3b candidate — it reintroduces an emailed token, so it stays out until needed).
- *Conflict with the canonical spec:* SPEC-CANONICAL.md does not include accounts in Phase 1 scope; accounts are **additive** — they touch no launch gate (≥15 sellers ✓ already 25, listing evidence rules unchanged, prices still hidden). The one intersection: the spec's claim/correct/remove flow is email-based today; accounts do not replace it at launch (claims keep working by email; account-based claiming is 3b). **Recommendation recorded: ship accounts as Phase 3 AFTER the Dec 16 launch scope is safe** — the filter phase and launch checklist are not blocked on accounts.

## 2a. Email verification — one-time 6-digit code (added 2026-11-16)

Every account's email address is verified once, at signup, with a **6-digit code the user types in** (directed by Dustin 2026-11-16 — a typed code, not just a link):

- At signup, a verification email is sent via Cloudflare Email Sending (§4) containing the code. The code is stored **hashed** (SHA-256 with a per-code salt — never plaintext), **expires in 30 minutes**, and allows **max 5 attempts** before it dies.
- **Resend** issues a fresh code and invalidates the old one (only one live code per user at a time). Resend is available from the verification prompt and the account page.
- Entering the correct code sets `email_verified = true` + `email_verified_at`.
- The account is created immediately and is fully usable (browsing, favorites, joining lists) — **but waiting-list notifications only ever send to verified emails**: an unverified account's waitlist entries sit inactive, and the waitlist signup itself prompts *"Check your inbox for a 6-digit code to activate notifications."* The publish-trigger matcher skips unverified users (their entries activate automatically the moment they verify — no re-join needed).
- **Changing the account email** resets `email_verified` to false and re-runs the same code flow for the new address.
- **Boundary (explicit):** this code is ONLY the one-time email-ownership check. Sign-in stays exactly as confirmed in §2 — name + email + phone, NO password, NO codes. Verification must never creep into a login-code flow.
- Admin notification emails to Dustin go to his verified admin address and are unaffected by user verification state.

## 3. Turnstile (required)

- One Turnstile widget per form (account create, sign-in, waiting-list join), invisible/managed mode.
- Server-side: the Worker POSTs the token to `https://challenges.cloudflare.com/turnstile/v0/siteverify` with the SECRET key before processing; missing/invalid token → 403 with a friendly, accessible error ("We couldn't verify that you're a person — please try again"). A submission without a valid token MUST be rejected — covered by an automated test.
- Keys: site key is public config (wrangler vars); **secret key is a Worker secret** (`wrangler secret put TURNSTILE_SECRET_KEY`), never in the repo, the report, or logs.
- Accessibility: Turnstile's managed widget is keyboard/screen-reader operable; the forms keep full labels and error text per WCAG 2.2 AA; if the widget fails to load (ad-blockers), the form explains and offers the mailto fallback for waiting-list requests at launch.

## 4. Waiting lists + notification plumbing

**Signup surfaces:** (a) zero-seller variety pages — primary CTA under "No sellers yet"; (b) any variety page — secondary "Join the waiting list" (for first-found notifications while it has no sellers; if it already has sellers the control is hidden at launch); (c) the account page lists all memberships with one-click leave. Signed-out visitors see the same control; joining prompts account creation inline (name/email/phone + Turnstile) and then joins the list — one flow, no dead ends.

**Trigger:** listings become visible at *publish* time (ingest API accept → catalog publish, and bulk catalog imports). After each publish completes, a matcher runs over the varieties whose listing count crossed 0 → ≥1 in that publish:
1. Find `waitlist_entries` for those varieties with `notified_at IS NULL`.
2. Insert one `notification_outbox` row per (user, variety) — UNIQUE constraint makes re-runs and overlapping imports safe (dedupe).
3. Mark entries `notified_at` when their email is actually sent (not when queued).

**Sending:** a scheduled Worker (cron, e.g. every 15 min) drains the outbox:
- Group by user: **one email per user per drain run**, listing every newly found variety in that run ("3 of your varieties were found") — a 500-variety import produces one email per affected user, not 500.
- Rate limits: max 200 emails per run; leftover rows stay queued for the next run. Global kill switch: a settings flag `notifications_paused`.
- Provider: **Cloudflare Email Service — Email Sending** (public beta since April 2026), via the Workers `send_email` binding — decided 2026-11-16. It covers all three transactional streams: (a) admin notification to Dustin on a farm-owner claim / Add Your Farm submission, (b) waiting-list "your variety was found" notifications, (c) account notices. Requirements fit: Workers Paid (already mandated by the canonical spec from day one); 3,000 emails/month included, then $0.35 per 1,000; transactional only (this design sends no marketing mail — a perfect fit). Setup: the sending domain must be onboarded in the hues.flowers zone, which adds locked DNS records (SPF/DKIM) for **seeds.hues.flowers**. From: `Seed Directory <found@seeds.hues.flowers>`; Reply-To: the Hues contact address. **Beta caveat:** no SLA yet — so all sending stays behind the tiny `sendEmail()` interface, and a provider such as Resend can be swapped in behind it if beta limits bite (no call-site changes). **Documented fallback (confirmed 2026-11-16): Amazon SES** — ~$0.10 per 1,000 emails and it allows marketing mail (Cloudflare Email Sending is transactional-only), but it starts sandboxed (needs a production-access approval) and would be a cross-cloud call from the Worker. SES becomes the route only if volume grows large or marketing mail is ever needed; until then it is a paper fallback behind the same `sendEmail()` layer. Inbound, if wanted later: Cloudflare Email Routing (free) can forward addresses like hello@seeds.hues.flowers.
- Every email carries: per-variety unsubscribe (signed token link, no sign-in needed), a global unsubscribe (sets `users.notify_opt_out`), and a "Manage your waiting lists" link. `List-Unsubscribe` header included. Footer carries the Hues Floral Park name + farm address (CAN-SPAM).

**"Your variety was found" email outline:**
> Subject: `Good news — {Variety Name} seeds found`
> Header: Hues dahlia mark + "Seed Directory · by Hues Floral Park"
> Body: "You asked us to watch for **{Variety Name}** ({Crop}). It's now listed by {Seller Name} — {link via /go/ so clicks are tracked}. {If several: a short list, each with its seller + link.}"
> "You're on the waiting list for N varieties. Manage your lists / unsubscribe from this variety / unsubscribe from all."
> Footer: Hues Floral Park, 93485 River Road, Junction City, OR · "You got this email because you joined a waiting list at seeds.hues.flowers."

**Demand data for Dustin (admin view):** waiting-list counts ARE the seller-hunting priority list. A token-gated admin page (same admin-token pattern as the ingest API) at `/admin/waitlist`: varieties ranked by waiter count (with crop, current seller count, waiters trend), total accounts, total active list memberships, recent signups, and the outbox status (queued/sent). Plus an optional weekly digest email to Dustin: "Top 10 most-waited varieties this week." No public exposure of counts at launch (a "12 gardeners are waiting" line on zero-seller pages is a nice social-proof candidate for 3b — Dustin's call).

## 4a. SMS alerts — the primary in-stock channel (added 2026-11-16)

Directed by Dustin: people don't check email often, so **waiting-list "your variety was found" alerts go by TEXT MESSAGE**. Channels: **SMS primary, email secondary — send both** (the email remains the full-featured version with all links; the text is the one expected to be seen). Everything else stays email as designed: verification codes, account notices, and the admin alerts to Dustin.

- **Provider:** AWS End User Messaging (Pinpoint) from Dustin's AWS project is the leading candidate, behind the same swappable-interface pattern as email (`sendSms()` beside `sendEmail()`; **Twilio is the fallback**). Costs: ~$0.006–0.01 per text plus sender-number rental. **Availability check (required before build sign-off):** End User Messaging must be verified against the new-experience FREE plan — run `aws freetier get-account-plan-state` (profile `hues`) and check the Free Tier supported-services list. NOTE 2026-11-16: the check could not be completed when specced — the AWS CLI session had expired and re-authentication needs Dustin's `aws login --remote` code; the plan state on record is FREE with $100 credits. If the service is not on the FREE supported list, the route is Twilio (or activating advanced features on the project — Dustin's call). The send layer is provider-agnostic either way, so this decision does not block the build.
- **Consent + compliance (US A2P / TCPA — mandatory):** the waitlist signup carries an explicit SMS opt-in — an **unchecked-by-default checkbox, "Text me when this variety is found,"** with standard consent language (message frequency, "msg & data rates may apply," reply STOP to end / HELP for help, consent is not a condition of purchase). Alerts go ONLY to opted-in numbers. STOP/HELP keywords are handled by the provider. A **registered sender is required before launch** — a verified toll-free number is the lightest path (toll-free verification) vs a full 10DLC brand+campaign registration; either way there is registration lead time (days to a couple of weeks), so registration starts early in the phase, not at the end.
- **Phone verification (per-number):** before the FIRST alert, the alert phone number must be verified with a one-time SMS code — this is where texted codes earn their keep. Same machinery as §2a email codes (6-digit, hashed, 30-minute expiry, max 5 attempts, resend invalidates) via the shared verification-code service. The account phone is the default alert number, but verification is **per-number**: enter a different alert number and that number gets its own code + verified flag. An opted-in but unverified number receives no texts (its alerts still go by email if the email is verified).
- **Message shape:** short, one text per variety per farm-arrival: `Seed Directory: {Variety} ({Crop}) is now listed by {Seller} — {short link to the variety page}`. No spam repeats: the dedupe rules in §4 apply per channel (one alert per user per variety per arrival event). A same-day multi-farm digest ("3 farms now list {Variety}") is a nice-to-have — noted as future work, not launch scope.
- **Provider lean + Phase 4 direction (recorded 2026-11-16, NOT a build):** Dustin is leaning **Twilio** for SMS, partly because Twilio also does voice — he wants the option of a full IVR people can call into. AWS End User Messaging has voice too, but Twilio's IVR tooling (TwiML/Gather/Studio, speech + keypad) is the stronger story, and that tips the provider decision toward Twilio. **Phase 4 candidate — the Seed Directory IVR:** callers reach the same toll-free number that sends the alerts and can (a) check whether a variety is in stock and which farms have it, (b) join a waiting list by phone (matters for gardeners who don't live on the web), (c) hear a farm's details, and (d) reach a human/Dustin by voicemail. Design principles when built: the IVR reads from the SAME catalog + waitlist data as the site (no second database of truth), phone-joiners get accounts created from their caller number + spoken name, and SMS confirmations close the loop. No build and no number purchase yet — the provider decision is still Dustin's to finalize; this records the IVR as a planned direction that favours Twilio.
- **Phone-only accounts (IVR phase, recorded 2026-11-16):** a caller who asks for a variety and wants the result sent to them gets an account created with **just their phone number — NO email required** (Dustin's explicit reasoning: spelling an email over the phone is error-prone). Their name is captured by voice on the call. Model changes to note for that phase: `accounts.email` becomes OPTIONAL (nullable); two account kinds — **full** (name+email+phone) and **phone-only** (name+phone). The phone number is verified by the channel itself: caller ID on the inbound call plus the confirmation-text loop (they receive the texts and can STOP them). A **verbal SMS opt-in is captured and logged on the call** before any alert enrolment. What phone-only users get: the found variety's farm buy link texted to them (the /go link), waitlist enrolment by voice, and future alerts by text; email-only features (email alerts, email verification) simply don't apply. **Upgrade/merge path:** a phone-only user who later comes to the website can add an email (verified by the usual one-time code, §2a) to the SAME account — match on phone number; if they web-signup with a phone that already has a phone-only account, merge rather than duplicate. **Web sign-in note:** phone-only accounts live primarily on the phone channel; do NOT invent a separate web login scheme for them in that phase — adding an email is their web door. Open design note for the IVR phase, not a blocker. (Nothing in Phase 3 changes: web accounts still require email; this only records the future model direction so the Phase 3 schema doesn't paint it into a corner — e.g. don't put a NOT NULL + UNIQUE on email without noting this.)
- **Starter account + finish-setup flow (IVR phase):** the account STARTS from the number they called in on — when a caller asks for a variety or joins a waiting list, the starter account is created keyed to their caller ID automatically (verbal consent captured on the call first). We then TEXT them to finish setting up their profile: the text carries a **secure, expiring finish-setup link** — the profile-completion page tied to that number (token-authenticated from the text; no login needed for this one completion flow) where typing is easy: confirm/add name, add email (verified by the usual one-time code), set alert preferences. This is the answer to the email-spelling problem: no dictating emails by voice — the typing happens on the web page the text points to. **Security:** finish-setup tokens are **single-use**, expire (suggest **7 days**, re-issuable by calling in or requesting a new text), and completing setup does not by itself grant farm-owner anything (that flow is unchanged).
- **Inquiries — the starter account is attached to what they called for (IVR phase):** every call that asks about a variety writes an **inquiry record** on the account at call time: account_id (from caller ID), variety_id (what they asked for), outcome — FOUND (with the farm/listing identified) or NOT FOUND (which creates their waitlist entry in the same step) — plus timestamp and source=IVR. Repeat callers are recognised by caller ID: the IVR can reference their existing inquiries/waitlists ("last time you asked about…"), and new asks append to the same account. **Data model:** waitlist entries and "found it for them" events are two states of the SAME inquiry record, so history reads as one list of "what you've asked us to find." Alerts fire off the inquiry's variety when a listing lands, exactly like web-created waitlist entries — one pipeline, two doors (web + phone).
- **HELD until the account is complete (Dustin's correction, 2026-11-16 — supersedes the earlier "nothing waits on profile completion" draft):** IVR-created inquiries are recorded and attached to the starter account, but **HELD**. The user must FINISH THEIR ACCOUNT FULLY before they get ANY notifications — no in-stock alerts, no result texts, nothing fires to an unfinished account. Corrected flow: call → inquiry recorded + attached, status HELD → the only outbound text is the finish-setup invitation itself (which therefore carries the setup link, and the result link only goes out after completion) → user completes setup (name + contact confirmation + SMS opt-in + ZIP on the setup page) → account marked complete → the held request ACTIVATES: if their variety was already found, the result goes out then; if not, their waitlist entry becomes live for future alerts. The IVR script says this plainly on the call: *"We'll hold your request — finish your profile from the text we're sending, and your alerts switch on."* Model: inquiry status **held → active on account completion** (an account-level `profile_complete` gate; web-created accounts are complete by construction once email/phone verification rules are met — the gate bites only on IVR starter accounts). If they never finish setup, the phone-only account still works when they call in again (the IVR recognises them and reads their held/active inquiries), but nothing is ever sent to it.
- **The account's ALERTS section (UX confirmation, 2026-11-16):** the user account has an **Alerts section** — their tracked varieties/inquiries with live status (waiting, or found-at-farm with the link). The moment an IVR-created account finishes setup, every variety they called about is already there in that alerts section — immediately available, nothing to re-enter or re-ask. Web-joined waitlist varieties live in the SAME section (one list, both doors). Notifications (text/email) are just the outbound echo of changes to this list — the list is the truth; the messages point back at it. (Phase 3 build note: the account page's waiting-list view IS this alerts section — build it as the inquiry list with per-item status, so the IVR phase plugs into the same surface.)
- **Returning-caller recognition (IVR phase):** if a caller already has a **completed** account, the IVR recognises them by caller ID (recognition key = the account's phone number matching the inbound caller ID) and greets them by name — *"Welcome back, {first name}"* (first name only). **Unfinished (held) starter accounts** get a friendly nudge instead: recognised as a starter account and reminded their requests are held until they finish setup from the text link (with an offer to re-send the link). **Privacy guardrail:** caller ID can be shared (a household phone) or spoofed — the first-name greeting is fine (low sensitivity), but the IVR must NOT volunteer private account details (email address, full inquiry history) unprompted; specifics come out only in answer to what the caller asks on the call.

## 4b. Phase 4 — the AI assistant: phone IVR + website chat (design, 2026-11-16 evening)

One assistant brain, two conversational doors (a third exposure — MCP — is specced in PRODUCT-DESIGN.md). This section records Dustin's evening direction; it supersedes the §4a draft fragments where they conflict (noted inline). Canonical consolidation: **PRODUCT-DESIGN.md**.

- **The phone service is AI-RUN and conversational — Dustin's explicit requirement:** it must feel like a conversation with a real person — a very communicative, helpful AI — NOT a press-1 menu tree. Free-form speech in, natural speech out; callers ask about varieties in their own words. **Stack:** Twilio carries the call; **Twilio ConversationRelay** (~$0.07/min + call minutes) handles speech-to-text + text-to-speech with natural voices (e.g. ElevenLabs); **the brain is our own LLM (Claude-class) running on our side**, wired to the SAME catalog / accounts / waitlist API as the site — account recognition, variety lookup, held-inquiry creation, and alert enrolment all go through that API. All-in-one agent platforms (Retell / Vapi / ElevenLabs Agents) are noted as faster-launch alternatives, not the plan — conversation logic and user data stay in our own stack. **Cost picture:** roughly **$0.40–0.50 per 5-minute call** all-in. **Persona:** warm, unhurried, knowledgeable gardener-host (consistent with the Hues voice); the AI identifies itself honestly if asked, but the default experience is conversational, not robotic disclaimers.
- **The FINAL smart-link flow (Dustin, 2026-11-16 — supersedes both earlier text designs: the "result waits entirely" draft in §4a and the "links + appended note" draft):** the post-call text carries **ONE smart link per inquiry** — tokenised, tied to the account + the inquiry, carrying the variety as its destination.
  - **Account INCOMPLETE:** the link lands on the finish-signup page first; the instant signup completes, the site **redirects them to the variety page they called about**. Their held inquiry activates at the same moment, so the variety page / Alerts state they land on is already live.
  - **Account COMPLETE:** the same kind of link goes straight to the variety page, no detour.
  - **Implementation rules:** the finish-setup flow accepts a post-completion redirect target **allow-listed to our own variety/seller pages only** (no open redirect), stored with the setup token. Multiple inquiries on one call → one text; the link carries the **most recent variety** as destination, the rest wait in their Alerts section. The AI explains it on the call in one breath: *"I'm texting you a link — it'll have you finish your account first, then take you straight to that variety."*
  - **Reconciliation with the HELD rule (§4a, which stands):** this smart-link text IS the finish-setup invitation — the single outbound text an unfinished account receives. Everything ongoing (in-stock alerts, further notifications) stays HELD until setup completes. Mid-call, when a variety is found, the AI offers the text and confirms on the call ("I've just texted that to you"); texts sent during calls use the same SMS pipeline + consent records as alerts (the call itself captures consent for the follow-up text).
- **Website AI chatbot — the third door (Dustin, 2026-11-16):** a chat bubble on seeds.hues.flowers opens the same assistant — same LLM brain + same catalog/accounts/waitlist API as the IVR. Core job: visitors can **ask for varieties not on the site**. Behaviour: (1) chat searches the catalog first — variety exists → answer with its farms/links (or its zero-seller status + one-tap waitlist); (2) variety exists but has no sellers, or is NOT in the catalog at all → the chat captures a **variety request as the same inquiry record** the IVR creates (attached to their account; anonymous chatters get the same finish-setup smart-link flow, held until complete); (3) the request triggers **the HUNT**: our agent scours the web for farms selling that variety — through the existing ingest discipline ONLY (evidence-quote validation; candidate listings/sellers land in Dustin's review queue; NOTHING auto-publishes; new varieties become catalog-expansion candidates for review). Verified finds fire the normal alert (text primary) to everyone waiting on that variety. **Guardrails:** the chatbot never invents listings, prices, or availability — if it isn't verified, the honest answer is "not found yet; you're on the list and we're hunting." Abuse controls: Turnstile + rate limits; hunt jobs count against the canonical spec's agent spend cap ($150/mo) and daily review budget, queued by demand (most-wanted varieties first — the waitlist counts already rank them). **Sequencing:** after accounts/alerts (it depends on inquiries + alerts existing); the IVR and chat share one assistant core, so build order between them is flexible.
- **Growing-knowledge scope (Dustin, 2026-11-16):** the assistant (both doors) also answers growing questions — which flowers are cool-weather vs warm-weather, which are easiest to grow, which are finicky, "all of those kind of details." **Grounding rule:** answers come from the site's own SOURCED fact base — the Phase 2 season/sowing classifications and the VARIETY-FACTS-SCHEMA attributes (season class, sowing method, difficulty, germination/maturity timing, spacing, support/pinching needs) — the same data that powers the filters, so the assistant, the filters, and the variety pages never disagree. Where a fact isn't sourced yet, the assistant says so plainly and can offer a waitlist/request — it does not improvise agronomy. **Difficulty** (easy/moderate/finicky) needs a sourced or Dustin-reviewed rating per crop before the assistant quotes it. This raises the value of fact-schema coverage work (crop-level facts first).
- **One knowledge base + advisory role (Dustin, 2026-11-16):** the growing knowledge lives in ONE curated **knowledge base** serving BOTH assistant doors — same facts, same answers, no drift between channels. New advisory use case: visitors ask things like "what FILLERS should I grow?" and the assistant gives SUGGESTIONS. That needs a **role/use attribute per crop** in the fact schema — focal / filler / spike-or-line / foliage / texture — sourced from Floret material where available, otherwise flagged for Dustin's review before the assistant quotes it (see VARIETY-FACTS-SCHEMA.md). Suggestion behaviour: combine role + season class + difficulty + what they're growing it alongside; land suggestions on real catalog entries wherever possible (varieties with sellers → links; without → waitlist offer), so advice always ends somewhere actionable. **KB governance:** facts enter the KB through the same sourced pipeline as everything else (source noted per fact); the assistant answers only from the KB + catalog, and says "I don't know yet" outside it.
- **Zones, frost dates, personalized timing (Dustin, 2026-11-16 — attributes specced in VARIETY-FACTS-SCHEMA.md):** USDA zone suitability per crop, a self-hosted ZIP→zone dataset (current USDA Plant Hardiness Zone Map, half-zones), a ZIP box on the site, average last/first frost dates per ZIP (NOAA-normals-based, labelled as 50%-probability averages), and per-crop timing rules (frost-offset windows) combined by a date-computation layer into gardener-specific calendar dates — quoted identically by pages and the assistant (one computation service). Accounts store ZIP + derived zone (see the header decisions), so the assistant personalizes by default for known callers/chatters.

## 5. Data model (D1, additive migrations only)

- `users` — id, name, email (UNIQUE, stored lowercased), phone (normalized digits), **`zip` (required at web signup; nullable only for IVR starter accounts until finish-setup completes it) + `usda_zone` (derived from ZIP at entry, e.g. "8b" — see the ZIP decision in the header and §6)** **`email_verified` (bool, default false) + `email_verified_at`** (§2a), notify_opt_out (bool, default false), status (active|banned), **`farm_owner_declared` (bool, default false — SELF-REPORTED at signup; intent only, grants nothing)**, **`is_farm_owner` (bool, default false — the VERIFIED flag, ADMIN-SET ONLY, see §9)**, **`seller_id` (nullable → sellers.id, the farm this account owns)**, created_at, updated_at, updated_seq not needed (not synced).
- `email_verification_codes` — id, user_id, code_hash (SHA-256 of the 6-digit code + per-code salt), expires_at (issued + 30 min), attempts (max 5, then the code is dead), consumed_at, created_at. A resend issues a fresh code and invalidates the previous one (only one live code per user).
- `phone_verification_codes` — same shape as email codes, keyed by (user_id, phone) — the SMS alert-number verification in §4a. One machinery, two channels: a shared verification-code service with a channel parameter.
- users gains for SMS alerts (§4a): `alert_phone` (nullable; defaults to the account phone), `alert_phone_verified` (bool), `sms_opt_in` (bool, default false) + `sms_opt_in_at`.
- `farm_owner_audit` — id, user_id, actor (admin identity/token label), action (granted|revoked), seller_id, created_at. Every flag change is recorded; the audit trail is append-only.
- `sessions` — id, user_id → users, token_hash (SHA-256, UNIQUE), created_at, expires_at, last_seen_at. Cookie: `sf_session` = raw token.
- `waitlist_entries` — id, user_id → users, variety_id → varieties, created_at, notified_at (NULL until sent), UNIQUE(user_id, variety_id).
- `notification_outbox` — id, user_id, variety_id, listing_id (the listing that triggered it, for the email link), queued_at, sent_at, status (queued|sent|suppressed), UNIQUE(user_id, variety_id).
- (3b) `favorites` — user_id, target_type (variety|seller), target_id, created_at, UNIQUE triple. (3b) `seller_ratings` — user_id, seller_id, stars 1–5, review text, status (pending|published|removed), created_at, UNIQUE(user_id, seller_id).

All account tables are **private**: excluded from the public sync/snapshot allowlist and the public API — the snapshot the native-apps sync ships must never contain user data. Guardrail test: assert users/sessions/outbox tables are absent from the snapshot allowlist.

## 6. Privacy & consent

- Collect the minimum: name, email, phone, ZIP. Purpose stated at the form ("to sign you in and email you when a variety is found"). **ZIP is stored as account data and never displayed publicly; features use the derived USDA zone, not the exact ZIP.** No tracking pixels in emails; no sale/sharing of data; waiting-list data is used for notifications + Dustin's aggregate demand view only.
- Account deletion: account page "Delete my account" → removes user, sessions, waitlist entries, outbox rows (ratings, in 3b, are anonymized not deleted, to keep seller scores honest — stated in the privacy note).
- A short privacy section joins /about/data (which already discloses Hues' ownership): what we store, why, how to delete it. Phone numbers are never displayed publicly anywhere; names appear publicly only on published reviews (3b, with a "show my first name only" default).

## 9. Add Your Farm — header CTA + self-submission (added 2026-11-16)

Dustin directed a prominent header CTA, **"Add Your Farm"** (the Seed Directory equivalent of hues.flowers' "Plan a Visit" primary button), shipping in the same phase as accounts because the plumbing overlaps:

- **Button:** the header's primary button (catalogue-styled, leaf-deep ground), beside the account icon; visible and tappable on mobile (the label is short enough to keep in full). It ships together with its destination page and with the account icon (Phase 3) — never as a dead button.
- **Destination:** an "Add Your Farm" page with a self-submission form (fields locked 2026-11-16, below). Turnstile-protected like the other human-only forms.
- **Form fields (locked 2026-11-16):** REQUIRED — (1) Farm name; (2) Contact name (prefilled from the account); (3) Contact email (prefilled from the account); (4) City; (5) State (dropdown; prefilled when arriving from a /state/{slug} page); (6) Website or online shop URL (needed for verification + the shop crawl); (7) About your farm — short text (feeds the profile-summary draft); (8) Varieties you want listed — free text, one per line (matched against the catalog on review); (9) "I own or am authorized to represent this farm" — required confirmation checkbox. OPTIONAL — Google Business Profile link (aids verification + review import); social links — Instagram, TikTok, and a Facebook business page link; sells wholesale too? (yes/no); anything-else notes.
- **Business phone (required, farm record):** a distinct BUSINESS PHONE field on the farm form — separate from the account phone. The account phone stays private forever (it is half the sign-in pair — never displayed anywhere); the business phone is the farm's own public contact number, collected on the farm record. It is REQUIRED (a farm listing needs a reachable business contact) and deliberately NOT prefilled from the account phone — the number they signed up with may be a personal cell, so the field starts blank for them to enter the business number on purpose.
- **Auto-drafted summary + pre-fill suggestions (build with this phase):** when a submission arrives with a website URL, an automated job — same family as the canonical spec's ingester (honest bot UA `HuesSeedFinderBot`, robots.txt respected, gentle pacing) — fetches the farm's homepage + About page and drafts the 2–4 sentence profile summary **in our own words**. It reuses the ingest API's evidence discipline exactly: every factual claim in the draft must be backed by a stored source quote from the fetched pages, and anything unbacked is dropped from the draft. The draft + its source quotes attach to the submission in the review queue as a **DRAFT — never auto-published**; Dustin approves or edits it during the same review that flips `is_farm_owner`. The job also extracts obvious structured facts (city/state, Instagram/TikTok/Facebook links, published business phone) as **machine-suggested values shown beside the submitted ones** — flagged as suggestions, never silently overwriting what the farm typed. Failure handling: unreachable/blocked site → the submission proceeds normally with no draft and a note on the queue item. (The same mechanism is how the 25 existing sellers' summaries can be drafted for review — the current seller summaries were produced by exactly this fetch-and-check discipline by hand.)
- **Declaration flow (signup):** the signup form carries a self-declaration control — "I'm a farm owner" (account type: Farm owner vs regular gardener). Declaring sets `farm_owner_declared = true` and routes the person straight into the Add Your Farm details (farm name, website/shop URL, what they grow/sell, varieties wanted), creating a **pending review-queue item pre-linked to their new account**. Form copy states plainly: *"Your account is ready to use right away. Farm-owner tools unlock after we review your farm — we'll email you when it's approved."* Declaring grants NOTHING by itself.
- **Queue, not publication:** submissions land in Dustin's review queue (the same claim/request + hand-approval model as the canonical spec — reuse the existing report/claim plumbing and /api/v1 patterns rather than a parallel system). Nothing auto-publishes; approval creates the seller record (and listing requests are worked through the evidence-based ingester as usual). **Every declaration also sends Dustin an admin notification email** (to his address on file for the project) the moment it lands — a new farm-owner claim should never wait for him to happen to open the queue.
- **Approval side-effect — the farm-owner flag:** when Dustin approves a submission whose submitter has (or creates) an account, the approval action in the same step sets `users.is_farm_owner = true` and links `users.seller_id` to the approved seller record, writing a `farm_owner_audit` row (who approved, when). The flag is **admin-set only** — it is never offered at signup or in the profile UI, and users cannot request it in-app (the Add Your Farm submission IS the request path).
- **Decline path:** the account simply stays a normal account (it was fully functional from minute one — waiting lists and all other gardener features are never held back pending verification); the declaration remains on record (`farm_owner_declared` stays true with the queue item marked declined), and the user is told farm-owner status was not approved.
- **Permission model (designed now, tools later):** future farm-owner tools (editing their own listings, managing their farm page) require `is_farm_owner = true` AND the target seller to equal `users.seller_id` — both checks, every time, server-side. This phase builds NO owner tools; it only establishes the flag, the link, and the checks' shape.
- **Revocation:** an admin can set `is_farm_owner = false` (audit row written). Revoking unlinks owner access immediately (owner-gated checks fail) but does NOT delete the account, its waiting lists, or favorites — the person keeps their gardener-side account; `seller_id` is retained for the record but confers nothing while the flag is false.
- The account icon (person icon, aria-label "Your account") also ships in this phase, linking to the account sign-in page.
