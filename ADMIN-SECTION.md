## Decisions so far
1. **Access — TWO LEVELS (Dustin, 2026-11-20):** Dustin = full admin (edit sellers, badge/classification calls, removals, everything). People he designates = **Reviewer level: review and approve only** — they work the queues but cannot edit seller records, flip badges, or remove sellers/listings. **Reviewer powers explicitly include determining duplicate varieties** (Dustin, 2026-11-20): the scout's POSSIBLE-DUPLICATE holds land in the reviewer queue for a duplicate / not-a-duplicate decision. **Duplicate outcome (Dustin, 2026-11-20): when a hold IS judged a duplicate, KEEP the held name as an alternate name on the existing variety** — it still turns up in search, and the scout never proposes it again. Never just discard it.
2. **Sign-in:** same as visitors — email + 6-digit code, no password. **Admin sessions last a long time: ~1 week** (Dustin's words).
3. **Scope:** opens on everything waiting for a decision (review queues first), then sections for sellers, listings, varieties & crops, and visitor accounts.
4. **Seller powers Dustin named explicitly:** edit a seller's information; determine whether they're a small farm or a large broker (the Small Farm badge / classification call moves into his hands in the UI; today it's Hue's judgment via the maintained classification record).
6. **Internal notes on seller details (Dustin, 2026-11-20):** the seller detail view in admin carries a notes section for INTERNAL notes — **never shown to the public**: not on public pages, not in any public API response; admin-side only, enforced server-side. **Reviewer-level designees can read AND add notes too (Dustin, 2026-11-20)** — notes are a shared team surface inside admin, still never public.

## Known needs the admin API already half-supports (candidates for the build)
- Review queue: seller candidates, queued (model-match) listings, scout POSSIBLE-DUPLICATE holds — approve / reject / publish.
- Sellers: edit info (incl. corrections like GeoSeed's Clinton → Greenwood, SC), badge on/off, deactivate/remove.
- Listings: retire (endpoint shipped 2026-11-20), re-point, restore.
- Catalog: varieties & crops — view/edit; scout direct-adds visible.
- Accounts: visitor accounts, `is_farm_owner` flag (currently admin-set only, no UI).
- Reports: /report submissions (seller_correction etc.).

5. **Statistics section — IN, and it's a real section, not just home counters (Dustin, 2026-11-20: "I also need all of those stats" + "We need like a statistics section so that we can see which varieties are popular"):** site stats (visitors, new accounts, waitlist signups) PLUS **popularity — which varieties are popular** is the named purpose. **Popularity signals — ALL OF THEM (Dustin, 2026-11-20):** variety page views; outbound seller clicks (the site already routes these through `/go/{listing_id}`); waitlist joins per variety; and search terms. Implementation note: raw visitor counts need a source — Cloudflare Web Analytics is the natural fit for this stack; per-variety popularity is better served by the site's own event capture than by an external analytics tool.)
