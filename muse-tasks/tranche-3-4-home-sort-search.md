## The work

1. **Home composition (§5.1; register B-5's remaining clauses).** `v2/app/page.tsx`: section order becomes hero → **Recently restocked and newly listed** → **Browse by crop** → How this directory works (Recently moves above Browse; content, badges, and the 6-item limit of Recently are unchanged). At rest (no home filter active) the Browse grid shows **12 crops**, ordered by varieties-with-sellers descending, then name ascending — deterministic, computed server-side from the coverage data the page already loads. A closing line under the grid reads "Showing 12 of {N} crops — see all crops" with the link to `/crop` (the count and the link are the contract). **When a home filter is active the cap lifts**: every matching crop shows, and the count line states the filtered total; §2.6.3's empty state covers the zero case. Boundaries: the hero prose measure is NOT touched (`max-w-2xl` stands — the 65ch cap is a later build), the header is not touched, crop-card artwork is not touched.

2. **Sort control (§5.2 as ruled; register B-6).** Surfaces: `/variety` and `/crop/[slug]` ONLY — not `/search` (relevance-ranked), not `/seller`, not the crop indexes (their absence is a decision, §5.2.1). Exactly three options: "Most sellers first" · "Name A–Z" · "Recently checked". A single-select chip group labeled "Sort", built from `.chip-filter`, rendered in the same control block after the filter groups and before the applied row, riding §2.5's in-place contract in full (one history entry per change, page reset to 1, count-line announcement, links as the no-JS floor). URL parameter `sort`: absent = Name A–Z (the ruling); `sort=availability`, `sort=name`, `sort=recent` are the explicit values. The availability order is defined exactly (§5.2.2): varieties with in-stock listings first, then varieties with listings, then varieties with none; within a tier, more listings first, then name ascending (the summary rows already carry `inStockCount`/`listingCount`; a new `availability` sort key or a composition of existing ones is your build input). "Recently checked" maps to the existing `-recently_checked`. The count line's ordering phrase follows the active sort — "…, most sellers first." / "…, alphabetical." / "…, most recently checked first." — and must never claim "alphabetical" under another order. **Sibling rail (§5.2.6):** the variety detail page's "More varieties" rail selects its six by the availability order instead of the first six alphabetical (ordering change only, no control).

3. **SearchBox — no-auto-open (§5.3.1; register B-8).** The panel opens ONLY in response to the visitor's own input in that box during this mount: typing (the existing 300 ms debounce) once the field's value differs from its mount value, or ArrowDown with results present. The mount value is submitted text, not typed text: **no fetch and no open occurs on mount**. Focus alone never opens the panel; `onFocus` may reopen only a panel the visitor's own typing produced in this mount. This holds on every SearchBox instance; `/search?q=zinnia` is the acceptance surface (results render, panel closed, no `/api/v1/search` fetch on mount).

4. **SearchBox — visible empty and failure rows (§5.3.3; register B-8).** When a visitor-typed query of ≥2 characters returns zero suggestions, the panel opens with one non-interactive message row: "No suggestions — press Enter to search." The row is never an option (never `aria-selected`, never activatable; Enter submits the search as today) and is `aria-hidden="true"` (the sr-only status line announces the identical text — one message, announced once). The failure state gets the same visible-row treatment with its existing text ("Suggestions unavailable. Press Enter to search."). This replaces the current `hidden`-on-empty behavior. No spinner; the debounce window stays silent.

5. **SearchBox — active-row state mark (§5.3.5, Ada AD-2; register B-8).** The active row gains a **3 px left rule in full-strength `leaf`** (`#1E4634` on surface = 10.42:1, past the 3:1 floor), applied to the same `active` state that drives hover and keyboard alike (one state, as today). The `bg-leaf-50` wash may remain as a redundant channel. ARIA 1.2 combobox semantics are unchanged (Ada's §7e pass stands). No other panel re-dress.

6. **Autocomplete ranking (§5.3.2; register B-8).** The service's combined results list orders by **match class first, type second**: class 1 — Exact (name, or a variety's alias, equals the query); class 2 — Prefix (a name, or a word of it, starts with the query — the varieties' existing tier 1, the same test applied to crops/series/sellers); class 3 — Substring / full-text (everything else that matches today). Within a class: varieties first (keeping their tier order and has-listings tiebreak), then crops, series, sellers, each alphabetical. Acceptance probes: `ali` → Alison above Calendula, California Poppy, Chinese Lantern, False Indigo; `Alison` → Alison first, then Alison Valentini; `sweet pea` → the Sweet Pea crop first; `mother of pearl` → exactly the one exact variety. **The results page's grouped layout does not change** — this contract governs the autocomplete's combined list only.

7. **Did-you-mean (§5.3.4; register B-8).** On the `/search` results page's zero-results state ONLY (never the autocomplete): if a near match exists, offer "Did you mean **Alison**?" as a link to that result's search. Candidate rule (the whole design): variety and crop names sharing the query's first letter with edit distance ≤2 (a transposition counts as 1), computed only when the result set is empty, over the name index the search already loads. At most one suggestion — the closest; ties break to the name with sellers, then alphabetical. No qualifying candidate → the state is exactly today's, unchanged. In the same touch, fix the U1.4 stray space inside the quoted query in that zero-results copy.

8. **Fold-in — 3.1b-2 test debt (small, bounded; do not expand it).** (a) Add handler-level contract tests for the crop-detail browse route — its payload carries the new `sort` state in this build, so its handler contract belongs in this build's coverage. ## Lessons fenced from this programme's history (binding)

1. **A green workflow gate does not mean the deliverable exists** — PRs #50 and #54 both certified incomplete builds. Before ending your turn, prove from the rendered surfaces (the app's own render tests / a local render) that: home shows the 12-crop cap in the computed order with Recently above Browse; `/variety?sort=availability` actually reorders by the tier rule; loading `/search?q=zinnia` renders results with the panel closed. Not just that the suite is green.
2. Lint as you go (`npx eslint .` after each file; refs never accessed during render). Type fixtures with the app's exported types at declaration. Run `npm run verify` after each test file and in full before ending; iterate until it exits 0 — ending red ends the run as a failure.
3. **Leave your work uncommitted.** The workflow's WIP and PR steps handle branching and commits; a fully-committed tree trips the no-changes guard and loses the run.
