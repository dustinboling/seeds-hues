## The build

### 1. Schema — migration 0018 (the next in sequence; additive only)

1. `sellers.customer_service_phone` — nullable text. The seller's customer-service phone **as published** (display form), populated only from the sweep dataset (§Data application). Distinct from any dialable form: the row renders the stored value as its visible text and derives the `tel:` href from it (digits, with country code) at render — the href and the visible text must describe the same number (Ada Ruling 2).
2. `sellers.customer_service_email` — nullable text. The seller's published customer-service email address, in full. SEPARATE from `contact_email` (which stays private and untouched by this build).
3. `seller_locations` — new child table, per SPEC-LOCATIONS F-L1's contract. Per location: seller FK; `kind` (`physical` | `warehouse` | `mailing` | NULL — NULL is the recorded "undetermined" state of §6.2: stored, never rendered, does not count toward the area minimum); address lines as published (street/PO Box line nullable; city; state; ZIP nullable — city + state are the minimum granularity); `is_primary` flag (exactly one primary per seller — enforce in the write path and assert in tests; the table may hold a seller's primary entry so the area can render it at published granularity); provenance (source URL + checked date, the sweep dataset's standard). Follow the schema file's existing conventions (enums as text with CHECK where the file does that, `created_at`/`updated_at` pattern, indexes on the FK).
   - **F-L2 fence:** `sellers.location` / `sellers.region` remain the primary and the ONLY values the header, seller index, state filing, and `PostalAddress` schema read. Nothing in this build makes any other surface read `seller_locations`. Additional locations never feed region derivation, state filing, or schema.
4. Drizzle schema (`v2/lib/db/schema.ts`) gains the two columns + the new table in the file's established style.

### 2. Write paths (admin family, established pattern)

Mirror the existing admin routes in `v2/lib/api/ingest-admin-routes.ts` (RouteSpec, scope `admin`, idempotent POST, Zod body via `parseBody`, `services.admin` funnel, Problem responses, revalidation behavior matching the family's seller routes):

1. `POST /api/v1/admin/sellers/:id/contact` — sets/clears `customer_service_phone` and/or `customer_service_email` (a field present-and-null clears; absent leaves unchanged — match the family's partial-update conventions if they exist, else state your choice in the PR body). Validation: phone is a non-blank string ≤ 40 chars when set; email must parse as an email address when set. This route NEVER touches `contact_email`.
2. `POST /api/v1/admin/sellers/:id/locations` — replaces the seller's whole location set with the body's set (the set is small; replacement is the idempotent shape). Validation per location: kind in the enum or null; city + state required (state a USPS code); ZIP optional; street line optional; **exactly one `is_primary: true`** in the set or the request is a 400 Problem; an empty set clears all rows. Provenance fields required per location (source URL + checked date).
3. Both routes covered by endpoint tests in the admin family's existing test style (authorized, unauthorized, unknown seller, validation failures, idempotent re-apply).

### 6. The shop catalog — tools, in-place layer, states

Composition per SPEC §3.3 + UI-DESIGN §§5–7, in order: H2 → control block (search, then filter groups, then sort) → applied row (when anything is applied) → count line → all-sold-out notice (when its state holds) → results region (grid) → pagination.

1. **Shop browse model — a new module `v2/lib/shop-browse.ts`** on the `lib/seller-browse.ts` / `lib/browse.ts` conventions (one home for vocabulary, state, URL encoding, counts, removers, count-line text; client-safe pure functions; the server page, the first-paint computation, and the hydrated layer share it so the three can never disagree). State: `{ crop, season, method, lifeCycle, hues: ColorFamily[], sort, q, page }`. URL params — no new names minted: `crop`, `season`, `method`, `life_cycle`, `color_family`, `sort`, `q`, `page` (SPEC §10.1). Parsing is forgiving exactly as specced: unknown values ignored → the all-values state, never a 404 — including `crop` (unrecognized → all-crops shop; a valid crop slug the shop does not stock → the §9.2 zero-combination state WITH the Crop remover, never a 404).
2. **Thresholds (SPEC §8):** T = the shop's own listing total (never the narrowed count). T = 0 → §9.1 empty shop, unchanged. T 1–8 → no tools (resting grouped order still applies). T 9–24 → filters + sort, no search. T ≥ 25 → search joins. Presence is a property of T in every state.
3. **Filter groups (S-3 + S-13):** order **Crop · Season · Sowing method · Life cycle · Hue** on the shared `BrowseFilters`/`FilterStrip` machinery and the Tranche 3 §2 behavior contract (same components, same chip dress, same parameter names). Crop is shop-only: single-select, plain-text chips (crop common names, NO swatch dot), "All" first then A–Z, no value cap, chip positions stable as counts change. All other groups single-select except **Hue multi-select** (PB-2: OR within Hue, AND across groups). **Discrimination (§5.2):** a group renders only if the shop's FULL set carries ≥2 distinct values with ≥2 non-zero counts. **Counts (§5.3 — the settled exception): computed LOCALLY from the whole shipped set**, server-side for first paint and client-side for updates, one definition in the shared model: an option's count holds every OTHER group's selection AND the current query; zero-count options render `0` and stay operable; the screen-reader unit is "listings" (CS-18) and the count belongs to the chip's accessible description (Ada Ruling 4).
4. **Sort (S-14):** the Tranche 3 §5.2 chip control (`SortChips` family), exactly three options in this order: **"In stock first"** (`sort=availability`) · **"Name A–Z"** (`sort=name`) · **"Recently checked"** (`sort=recent`). Absent `sort` = "In stock first". The grouped order: orderable (`in_stock`, `preorder`) above not-orderable (`unknown`, `shop_closed`, `sold_out`), **variety name A–Z the sole key within each section** — the former five-tier order no longer exists anywhere in the shop's sort. "Name A–Z" is pure A–Z; "Recently checked" is ungrouped, freshest first. **Ordering only** (UI-GRID-CARD §11): no section headings, dividers, boundary gaps, or ground changes — the grid's 8px gap is uniform across the invisible boundary; the resting "In stock first" chip carries the selected dress from first render. The grouped order is the resting order at EVERY band including un-tooled shops. Shop only: `/variety`'s default stays pure Name A–Z (PB-1 untouched, SH-21). While a query is active the sort group is ABSENT and relevance owns the order; the prior sort selection is restored when the query clears.
5. **Search (S-2; T ≥ 25 only):** a plain GET form — `role="search"`, action = the shop URL, input `type="search" name="q"`, visible submit "Search" (CS-08). **NOT the SearchBox combobox; no autocomplete panel** (PB-S1, settled exception). Visible label bound programmatically to the input (a real `<label>` or `aria-labelledby` — eyebrow styling on an unassociated span FAILS Ada Ruling 6): **`Search {name}'s shop`** (CS-06, `.eyebrow` dress above the field). Placeholder CS-07 verbatim: `Variety or flower name…`. Field dress per UI-DESIGN §6.2 (SearchBox `md` geometry: 48px height, `radius.search`, 2px line-strong border on surface, SearchIcon left, submit inside right; focus = leaf border + global ring; no hover/filled/disabled/error dress). Behavior: as-you-type from **2 characters**, ~300ms debounce, in place, **focus never leaves the field**; matches **variety name + crop common name only** (never Latin names, never aliases); match classes exact → prefix → substring order the results while a query is active. Search ∧ filters = AND, always; neither resets the other. In-shop searches are NOT written to the search log (SPEC §6.7/OQ-8 posture for this surface: no logging call from the shop layer).
6. **Applied row (S-5):** one remover per active group, one per selected hue, plus one search remover (`Search: “{q}”`, curly quotes) — labels/accessible names per CS-12 (`{Group}: {Value}`; `Remove the {Group} filter, {Value}`; `Clear the search for {q}`). Clear All ends the row with CS-13's two variants (`Clear all filters` / `Clear search and filters` when a query is active); one action clears filters AND query — **never sort**. **Focus landing (Ada Ruling 7, binding):** on any activation that unmounts its own control — if the applied row remains → focus lands on Clear All; if the row is removed → focus lands on the "{name}'s shop" `<h2>`; the count announcement is unchanged in both cases; focus never falls to `<body>`.
7. **Count line (S-4):** the persistent live region `#seller-results-count` (`aria-live="polite"`, `aria-atomic="true"`, present before any change, NEVER remounted), dress unchanged in every state (serif body, muted, `tabular-nums`). Forms verbatim (CS-14…CS-17): rest `{N} listings, in stock first.` · `{N} listings, A–Z.` · `{N} listings, most recently checked first.` · searched `{N} matches for “{q}”, best match first.` · pagination suffix as shipped (`· page {p} of {pages}` pattern per CS-14). The phrase never changes when one grouped section is empty. Exactly one announcement per deliberate change; per-settled-update announcements while typing are correct (Ada Ruling 5).
8. **In-place discipline (S-7):** after hydration, filter/search/sort changes update IN PLACE — no document navigation, no skeleton, no scroll loss, no page-view beacon. The mechanism serves the contract (SPEC §11.2–11.3): counts/narrowing/ordering are computed from the shipped full set by the shared model, identically on server first paint and client updates. History per §10.2: one deliberate change = one entry; **typing creates NO entry per keystroke** (replaceState while typing; pushState on submit / blur-with-changed-query / clear); Back restores in place and never exits the shop over a shop-state change. Any filter/search/sort change resets pagination to page 1. The results region carries the shipped pending discipline (aria-busy while a change is in flight + the `browse-pending` cue past ~200ms, per the D-B1-2 build) exactly as the other in-place regions do. Update failure (§9.5): prior state stands, ONE in-place `role="alert"` line with the applied row — CS-24 verbatim: `That didn't apply — you're still seeing the previous results. Try again.` (typographic apostrophes) — focus stays on the activated control, the count line does not change, the line clears on the next successful change. (With local computation this state is a contract backstop; implement it on the same commit path the other surfaces use, do not delete it as unreachable.)
9. **States:** zero-combination (§9.2): CS-19 as fixed by Wren — **`No listings in {name}'s shop match those filters.`** — inside the results region, applied row stays, Clear All recovers in place, focus per §5.7/Ruling 7. No-matches (§6.5): CS-20 `No matches for “{q}” in {name}'s shop.` + (only when filters are also active) CS-21 as a standalone line `With the current filters applied.` (capital W, no leading ellipsis) + bounded did-you-mean (CS-22 `Did you mean {candidate}?`, candidate = in-shop variety/crop names only, same first letter, edit distance ≤2, at most one, ties → stock then alphabetical; the candidate link stays inline in its sentence per Ada Ruling 3).
