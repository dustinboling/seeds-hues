## The work (per SPEC §3.6's change list)

1. **The alert step** (`WaitlistBlock.tsx` rebuilt per §3.2): signed-out resting state = heading + existing one-alert copy (unchanged) + **Email** field + **channel choice** as compact radio rows in a real fieldset/legend ("Email only" default / "Email and text") + "Join the waiting list". No name, no ZIP, no account type on this step. Choosing text reveals the **Phone** field directly under the radio (required for that channel only; focus never moves on reveal; switching back hides it and the phone is not submitted), with the existing sign-in explanation and the settled SMS consent copy beside the choice — the choice IS the opt-in; no separate opt-in checkbox. `SignupFields` is NOT consumed here anymore and is NOT changed by this item (§3.6).
2. **Minimal create in place** (service contract §3.3): one submit creates the account with exactly what the alert needs (email; phone iff text chosen; name unset, zone null, type defaults to gardener) and records the join in the same request pattern as today (`join_variety`). The success machinery — States A–D, the verification hold, the celebration + next-step card, the deliberate focus discipline, the leave action — is preserved exactly. The empty-string sentinel is treated as unset everywhere it surfaces (never rendered as a value).
3. **Recognized contact, inline** (§3.2.4 + §3.3's contract): an existing email never produces an error and never a link away — the block transitions in place to the code state with §3.2.4's copy and the shared `CodeEntry`; the service issues the code **without a session**, **rate-limited by the existing verification service's limits** (the create path's `enforceLimits: false` precedent is explicitly NOT carried over), records the pending join with the issued code, and **successful verification establishes the session at verify time and completes the pending join in the same step**. The "Sign in, then come back" line is deleted. Nothing about the account is disclosed beyond what the copy shows the submitter themselves.
4. **Finish-your-account step** (§3.2.5): after joining, in the success state's next-step card area (below the alert status, never interleaved), a dismissible, clearly optional step offers name / ZIP / account type with §3.2.5's copy; email and phone are never re-asked. The same step appears equivalently in `AccountPanel.tsx` for waitlist-created accounts until completed.
5. **The §11.1 accommodation** (`/account`): an account with no phone is offered **"Email me a code instead"** at sign-in — the code path verifies and establishes the session, so a flip-created account is never a dead end at /account either.
6. **The no-JS floor** (§3.4 + Ruling 9): the variety page server-renders the block's real content (heading, copy, the alert-step form as a plain HTML form; phone visible, labeled as needed only for text alerts, **never `required`** in the floor markup; the server enforces phone-iff-text). The skeleton/"Loading waiting-list status…" server output is **deleted** — a loading shell may appear only after a JS status fetch begins. The plain POST (form-encoded endpoint, **Turnstile-exempt per §11.4 with §3.4.5's compensating controls**) redirects back to the same variety page **with the block's fragment** carrying the resulting state — joined-and-verify (with a plain code form that also posts without JS), recognized-contact, joined-and-active, or the error state with entered values and channel selection preserved — and the server renders that state into the block. With JS, hydration replaces the floor form only after the status fetch resolves; **a failed fetch leaves the floor form on screen** with the brief status note. The listing-state gate stands server-side: the block renders only on zero-seller variety pages.
7. **Signed-in path unchanged** (§3.2.6): one-click join, existing states, existing leave.
